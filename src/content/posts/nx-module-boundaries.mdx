## Introduction

When working in a nx monorepo most of the code is organized in many different modules (libraries). These modules can be imported in other modules or applications and this dependencies formulate a dependency graph. In a growing project like this where you have too many different teams working on many different modules, it is crucial to be able to enforce some rules about the architecture of the project. For example in a lot of projects like this, a Domain Driven Design architecture is followed. 

### graph

![graph](/assets/blog/nx-module-boundaries/graph.png)

- preffered duplication and encapsulation over API pattern.

However any architecture in order to be followed from all the developers, ideally there should be rules in place that enforce it. Otherwise there is a high chance that after a while the architecture won;'t be folowed.


- vertical business-oriented sections
- a structure that remains maintainable,
- Low Coupling
- Enabling autonomous teams
- Reduce cognitive load - discoverable
- Lack of organization slows down engineers
- Lack of organization slows down CI
- Avoid excessive merge conflicts
- Avoiding cross-team dependencies
- Modular monolith

Applied Rules:
First dimension - Scope rules
- An application can import dependencies only from libraries, not from other applications.
-   - The libraries an application depends on are only of type `shell` and of type `model`.
- Libraries in the learnings domain can depend only on libraries that belong in the same domain or libraries that belong to the shared domain. They cannot depend on libraries from other domains (strict isolation) and of course they cannot import from the application. 
-   -  The libraries of type feature can depend on any other type of libraries (from the same domain because of the previous rule).
-   -  The libraries of type data-access can depend on "type:util", "type:model", "type:data-access"
-   -  The libraries of type ui can depend on "type:util", "type:model", "type:ui"
-   -  The libraries of type model can depend on "type:model"
-   -  The libraries of type util, can depend on "type:model", "type:util"
-   -  The libraries of type shell, can depend on "type:shell", "type:model", "type:feature"
-   -  The libraries of type feature, can depend on "type:feature", "type:model", "type:data-access", "type:ui", "type:util"
- Libraries in the users domain can depend only on libraries that belong in the same domain or libraries that belong to the shared domain. They cannot depend on libraries from other domains (strict isolation) and of course they cannot import from the application.


### 3. Sheriff

```ts
export const config: SheriffConfig = {
  entryFile: 'apps/learning-webapp/src/main.ts',
  enableBarrelLess: true,
  modules: {
    'libs/<scope>/feature-<feature>/src': ['scope:<scope>', 'type:feature'],
    'libs/<scope>/utils-<util>/src': ['scope:<scope>', 'type:util'],
    'libs/<scope>/<type>/src': ['scope:<scope>', 'type:<type>'],
  },
  depRules: {
    'root': ['type:shell', 'type:model'],
    'scope:*': [sameTag, 'scope:shared'],
    'scope:shared': 'scope:shared',
    'type:feature': [
      'type:feature',
      'type:model',
      'type:data-access',
      'type:ui',
      'type:util',
    ],
    'type:data-access': ['type:util', 'type:model', 'type:data-access'],
    'type:ui': ['type:util', 'type:model', 'type:ui'],
    'type:model': 'type:model',
    'type:util': ['type:util', 'type:model'],
    'type:shell': ['type:shell', 'type:model', 'type:feature'],
  },
};
```
