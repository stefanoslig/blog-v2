## Introduction

In a previous [article](https://www.stefanos-lignos.dev/posts/how-to-organize-libs-nrwl-nx), I gave an example of how you can organise your libraries in an Angular nrwl/nx monorepo. In this article, we're going one step further and I show to you how you can enforce module boundaries and dependency rules for these libraries. I present three different ways to do this with examples, the advantages and the disadvantages of each one of them. 

Before we start let's clarify the two terms I'm going to use throughout the article:

- **Module boundaries** - It specifies what parts of a module are accesible from outside. All the other parts should not be accessible. For example in an nx library that means that other libraries or apps can access only what is defined in the `index.ts` file of this library and taht deep imports are not allowed.

- **Dependency rules** It specifies which modules are permitted to depend on which other modules. It's more about defining a structure throughout your project. For example that only specific libraries can be imported from an app.  

<Aside type="note">
  To showcase these tools I used the same [github repo](https://github.com/stefanoslig/organize-nx-libs-article-demo) I used in my previous article. There are three different branches, one for each one of the tools:
  - Nx Module Boundaries (branch)
  - Dependency cruiser (branch)
  - Sheriff (branch)

When working in a nx monorepo most of the code is organized in many different modules (libraries). These modules can be imported in other modules or applications and these dependencies formulate a dependency graph. In a growing project like this where you have too many different teams working on many different modules, it is crucial to be able to enforce some rules about the architecture of the project. For example in a lot of projects like this, a Domain Driven Design architecture is followed or a  Hexagonal Architecture or your custom Architecture defined from your team. Maintaining an architecture like this in a monorepo can bring a lot of benefits:

- It enables autonomous teams that can work on their own features avoiding cross-team dependepncies and conflicts.
- It increases the disceoverability in the code and it reduces the cognitive load for the developers.
- It enables low coupling between the libaries which can also improve CI pipelines times since less projects are affected.

The challenge you will encounter sooner or later is when multiple teams touch the same codebase, if there are no rules in place to enforce programmatically the selected architectrue, slowly the architecture starts to alter and deform.

In the demo project, I have followed an Architecture which you can observe in the following graph. 

![graph](/assets/blog/nx-module-boundaries/graph4.png)

Two things to notice in the graph are:

1. The arrows on every domain going only down. That means that a lower level layer of the architecture cannot have dependencies from an upper level layer.
2. The second thing is that as you can see, the domains are strictly encapsulated. The domains (users / learnings) don't have any dependency from each other.  Deliberately, I prefered duplicating code than losing the library's encapsulation. Some teams prefer adding an API layer in each library from where they share Domain specific logic to other domains but from my experience I'm against this pattern since it gradually opens the door to more and more logic to be shared which at the end becomes unmanageble.

The above project has the following structure:

```
apps
    > my app
libs
    > learnings
        > data-access
        > feature-list
        > feature-search
        > feature-shell
        > model
        > utils-testing
    > shared
        > data-access
        > ui
        > model
    > users
        > data-access
        > feature-list
        > feature-search
        > feature-shell
        > model
        > utils-testing
```

To maintain this architecture, I will enforce the following rules:

### Rules

#### Module Boundaries Rules
- Every module can be accessed only through a public API which is defined in the `index.ts` file under the `src` folder of the module. If an index file is not provided then the module is fully encapsulated (which mean that it can only import other modules).

#### Dependency Rules

##### Scope-Related Rules

| **Scope** | **Allowed Dependencies** | **Restrictions** |
|-----------------|--------------------------|------------------|
| **Application** | Libraries only (no applications) | Cannot import from other applications |
| **Learnings domain** | Libraries in the same domain<br/>Libraries in the `shared` domain | Cannot depend on libraries from other domains<br/>Cannot import from applications |
| **Users domain** | Libraries in the same domain<br/>Libraries in the `shared` domain | Cannot depend on libraries from other domains<br/>Cannot import from applications |

---

##### Type-Related Rules

| **Module Type** | **Can Depend On** |
|------------------|-------------------|
| **feature**        | feature, model, data-access, ui, util |
| **data-access**    | util, model, data-access |
| **shell**          | shell, model, feature |
| **ui**             | util, model, ui |
| **application**    | shell, model  |
| **util**           | model, util |
| **model**          | model |

With these rules in place I can be sure my arhitecture can offer the benefits I want in my team and I can set the boundaries I want for my modules. Let's see now what tools we have in order to enforce it programmatically.

### Tools 

In my demo project, I have integrated three tools to enforce the afforementioned tools. There might be more tools out there but these are the tools that I found more interesting to describe in this article.

#### 1. Nx Module Boundaries

This is the official solution from NX. It's also the simplest solution since it's build-in and it doesn't require any dditional packages in order to work. Spoiler alert, this simplicity comes with limitations, meaning that it's the least flexible solution. You can apply rules only in library level by assigning tags in the `project.json` file. If your project is structured differently and you need to apply rules on sub-folders level, this is not possible.

##### Setup

To enforce module and dependency rules with `Nx Module Boundaries` you need to:

1. Add `tags` on every library. I used two kind of tags(scope, type) in this demo project. Read how multidimensional tags can make our rules better [here](https://nx.dev/recipes/enforce-module-boundaries/tag-multiple-dimensions).

```json
{
  "name": "learnings-data-access",
  "$schema": "../../../node_modules/nx/schemas/project-schema.json",
  "projectType": "library",
  "sourceRoot": "libs/learnings/data-access/src",
  "tags": ["type:data-access", "scope:learnings"],
```

2. After you have defined for each one of the projects, the tags, you can set the rules I defined before in the eslint configuration of the project.


#### Pros
- It's a built-in solution, it doesn't require additional external dependencies. It is maintained from the NX team.
- It's integrated with ESLint
- Scales well

#### Cons
- It’s not flexible. Rules cannot be defined at the folder level but only on a project level.
- Does not support complex rules. We will see how with the other two tools we can define more generic rules reducing boilerplate.


#### 2. Dependency cruiser

[Dependency Cruiser](https://github.com/sverweij/dependency-cruiser) is a framework agnostic tool which you can use to validate the dependency and module boundary rules you have configured. Using it, you can visualize all your dependecies in a graph. The violated rules can be reported either in the graph itself or in text format. This tool is the most flexible between the three I'm presenting in this article and also the most powerful since apart from defining and validating Dependency rules, you can also use it to identify circular dependencies, orphans, code that it's declared as shared but in reality is imported only in one other module, etc.

##### Setup
Once the dependency-cruiser package is installed and you have run `npx depcruise --init`, a `dependency-cruiser.js` configuration file is generated. This file includes general rules that are useful for any project, such as detecting circular dependencies and dead code. You can remove some or all of these rules if you don't need them in your project. After that you can simply add your rules and the messages the user will see if the rule is violated.

```js
{
    name: "no-cross-domains",
    comment:
    "One library should not depend on another domain's library. Dependencies from shared are allowed.",
    severity: "error",
    from: {
    path: "^libs/(?!(shared))([^/]+)"
    },
    to: {
    path: "^libs/(?!(shared))",
    pathNot: "^libs/\\$1"
    }
},
{
    name: "no-lib-to-app-deps",
    comment:
    "One application should not depend only on shell or model libraries. ",
    severity: "error",
    from: {
    path: "^apps/"
    },
    to: {
    path: "^libs/",
    pathNot: "^libs/[^/]+/(?:shell|model)(?:/|$)"  
    }
},
{
    name: 'data-access-lib-restricted-deps',
    comment:
    'Libraries of type data-access should depend only on libs of type data-access, model or utils-testing',
    severity: 'error',
    from: {
    path: '^libs/[^/]+/data-access'  
    },
    to: {
    path: '^libs/',
    pathNot: '^libs/[^/]+/(?:data-access|model|utils-testing)(?:/|$)'
    }
},
{
    name: 'ui-lib-restricted-deps',
    comment:
    'Libraries of type ui should depend only on libs of type util, model or ui',
    severity: 'error',
    from: {
    path: '^libs/[^/]+/ui'  
    },
    to: {
    path: '^libs/',
    pathNot: '^libs/[^/]+/(?:util|model|ui)(?:/|$)'
    },
},
{
    name: 'model-lib-restricted-deps',
    comment:
    'Libraries of type model should depend only on libs of type model',
    severity: 'error',
    from: {
    path: '^libs/[^/]+/model'  
    },
    to: {
    path: '^libs/',
    pathNot: '^libs/[^/]+/(?:model)(?:/|$)'
    },
},
{
    name: 'util-lib-restricted-deps',
    comment:
    'Libraries of type util should depend only on libs of type model or util',
    severity: 'error',
    from: {
    path: '^libs/[^/]+/util'  
    },
    to: {
    path: '^libs/',
    pathNot: '^libs/[^/]+/(?:model|util)(?:/|$)'
    },
},
{
    name: 'shell-lib-restricted-deps',
    comment:
    'Libraries of type shell should depend only on libs of type shell, model or feature',
    severity: 'error',
    from: {
    path: '^libs/[^/]+/shell'  
    },
    to: {
    path: '^libs/',
    pathNot: '^libs/[^/]+/(?:shell|model|feature-[^/]+)(?:/|$)'
    },
},
{
    name: 'feature-lib-restricted-deps',
    comment:
    'Libraries of type feature should depend only on libs of type feature',
    severity: 'error',
    from: {
    path: '^libs/[^/]+/feature-[^/]+'  
    },
    to: {
    path: '^libs/',
    pathNot: '^libs/[^/]+/(?:feature-[^/]+|model|data-access|ui|util)(?:/|$)'
    },
},
```

##### Pros
- Very flexible, framework agnostic
- You can set rules also in the folders level, it doen't depend on the tags you set in each project.
- Can be used as a more general code quality tool, to identify dead code or circular dependencies. For example, ensuring that a module in a shared library is imported by at least two domains; otherwise, if it is only used by one domain, it should belong to that domain instead of the shared library.
- You can visualize the violated rules

##### Cons
- Not integrated with ESLint.
- Steeper learning curve due to the extended capabilities and richer API it gives you. 

#### 3. Sheriff

[Sheriff](https://github.com/softarc-consulting/sheriff) is a tool designed to enforce module boundaries and dependency rules in TypeScript projects. It's framework agnostic like `Dependency cruiser` and also more powerfull than the built-in solution that nx offers. For example you can also set more fine-grained rules in the folders level (it doesn't depend on the tags of the project.json). However, you cannot add more generic related to code quality rules as you can do with `Dependency cruiser`. It works well with Angular and NX projects (the core maintainer is a GDE for Angular)

Setup

Once the `@softarc/sheriff-core @softarc/eslint-plugin-sheriff` packages are installed and you run `npx sheriff init`, a `sheriff.config.ts` configuration file is generated. 

```ts
export const config: SheriffConfig = {
  entryFile: 'apps/learning-webapp/src/main.ts',
  enableBarrelLess: true,
  modules: {
    'libs/<scope>/feature-<feature>/src': ['scope:<scope>', 'type:feature'],
    'libs/<scope>/utils-<util>/src': ['scope:<scope>', 'type:util'],
    'libs/<scope>/<type>/src': ['scope:<scope>', 'type:<type>'],
  },
  depRules: {
    'root': ['type:shell', 'type:model'],
    'scope:*': [sameTag, 'scope:shared'],
    'scope:shared': 'scope:shared',
    'type:feature': [
      'type:feature',
      'type:model',
      'type:data-access',
      'type:ui',
      'type:util',
    ],
    'type:data-access': ['type:util', 'type:model', 'type:data-access'],
    'type:ui': ['type:util', 'type:model', 'type:ui'],
    'type:model': 'type:model',
    'type:util': ['type:util', 'type:model'],
    'type:shell': ['type:shell', 'type:model', 'type:feature'],
  },
};
```
